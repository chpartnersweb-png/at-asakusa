# AT ASAKUSA｜1ページWebサイト制作計画

作成日：2026年11月12日  
対象：既存のAstroプロジェクト。今回は制作計画までとし、サイト本体の実装・公開は含めない。

## 1. コンセプト

**「浅草に、わが家のような旅の拠点を。」**

観光の楽しさと、部屋に戻ってくつろぐ時間をひと続きに感じられるアパートメントホテルとして紹介する。家族・グループが、広さ・設備・階段の条件を理解して自分たちに合う階を選び、予約サイトへ進めることを目的にする。

デザインの軸は、実際の写真にある青緑の壁、畳、木の家具と、logo.jpgの黒い格子・朱色の丸。建築的に整えたグリッドへ、大小の写真と余白を組み合わせる。見た目の変化には滞在の物語上の役割を持たせる。

メインコピー案：

> 浅草に、
> わが家のような旅の拠点を。

サブコピー案：

> ふたつの寝室と、いつもの暮らしの道具。
> みんなで過ごす東京に、くつろげる場所を。

冒頭で「全室2ベッドルーム／約30㎡／推奨4名・最大6名」を見せる。推奨人数を添え、最大人数だけで広さを判断させない。

## 2. 参考サイトの取り入れ方

### LANDIC採用サイト

https://www.landic.com/recruit/

ブラウザで、写真の上に独立した大きな日本語コピー、幅広い写真、スクロールに伴う画面展開、追従ナビゲーション、プロジェクト紹介の左側インデックスと右側の写真・文章を確認した。

取り入れるのは、余白と文字の強弱、写真を大きく見せる比率、スクロールに合わせて段階的に内容が現れる進行、見出しと写真の非対称な関係。AT ASAKUSAでは旅行者が早く客室・条件・予約へ到達できる長さに調整する。

参考サイトが使用するライブラリや内部実装は未検証。以下のLenis・GSAP仕様はAT ASAKUSA向けの提案である。

### MIMARU

https://mimaruhotels.com/

家族・グループが一緒に過ごす価値、キッチン等の設備を滞在の便利さへ結び付ける説明、FAQと予約への接続を参考にする。施設情報・サービス内容はユーザー提供のAT ASAKUSA情報に限定する。

logo.jpgをヘッダーとフッターに使用する。元画像の縦横比とマーク・文字の関係を保ち、背景を含めて馴染む配置にする。色変更・変形は行わない。格子・丸のモチーフは周辺の装飾として使う。

大見出し、導入、客室、設備、アクセス、予約でそれぞれ配置の役割を変える。おすすめTop5は、写真を大きく使う客室紹介と、暮らしの道具を見せる設備紹介に自然に組み込み、同じ説明の繰り返しを避ける。

## 4. ページ構成

### 00｜ヘッダー

左にロゴ、中央に「客室／設備／周辺・アクセス／ご利用案内」、右に「お部屋を選んで予約」。予約ボタンはページ内の階選択へ移動する。

PCは薄い不透明背景の固定ヘッダー。本文のアンカー位置にはヘッダー高の余白を確保する。スマートフォンはロゴ＋メニューボタンに整理し、下部に予約ボタンを配置する。メニュー表示時は背景スクロールを止め、閉じると元の位置へ戻す。

### 01｜ファーストビュー：写真の前に、宿の言葉を置く

PCは左上に大きな2行コピー、右側に小さな施設説明。その下に横長の客室写真を配置する。写真の上へ長い文章を重ねず、畳・青緑の壁・家具を十分に見せる。

写真の下に「全室2ベッドルーム／約30㎡／推奨4名・最大6名」と「客室を見る」。初期表示から予約への移動も可能にする。

スマートフォンは、コピー→写真→基本条件の順。写真を端末の高さに合わせて無理に縦長へ切り抜かず、4:3程度の比率を基準に構図を調整する。

### 02｜コンセプト：観光のあとも、旅を楽しめる場所

左に外観の縦写真、右に短い本文と室内の小さな写真。上下の開始位置をずらし、建物から部屋へ入っていく流れを作る。

説明は「浅草寺やかっぱ橋エリアへアクセスしやすい」「全室2ベッドルーム・フルキッチン」「目の前に公園」の3点。公園は文章で紹介し、写真素材が確認できるまで客室や道路の写真を公園写真として扱わない。

### 03｜客室：一緒に過ごす時間と、それぞれの休息

ページの主役。PCでは左約25%を小見出しとインデックス、右約75%を写真と説明へ割り当てる。左のインデックスはこのセクション内だけCSS stickyで追従させる。実際の文字量に合わせて高さを確保する。

1. **みんなでくつろぐ**：畳のある客室の大きな横写真。
2. **ふたつの寝室で休む**：別室のベッド写真と説明。写真の客室・寝室対応を確認してから表記。
3. **階ごとに、滞在を選ぶ**：1階テラス／2〜3階バルコニー／4〜5階バルコニーを、階の図解と横長の予約リンク行で示す。

共通条件は1回にまとめる。「約30㎡・2ベッドルーム・推奨4名・最大6名」。寝具数・ベッドサイズ・間取りは未提供なので記載しない。

**「エレベーターはありません。上階へは階段をご利用いただきます。」を客室紹介と階選択の両方に表示する。** 1階をバリアフリーと表記しない。4〜5階だけに眺望等の未確認の価値を付けない。

スマートフォンは左側インデックスの追従を解除し、写真→見出し→説明の縦配置にする。ページを横方向に移動させるスクロール演出は採用しない。

### 04｜設備：旅先でも、暮らしのペースで

キッチンの横写真、調理器具の縦写真、ワークデスクの寄り写真を、共通グリッド上で大きさを変えて配置する。写真枠と本文枠は通常の文書フローで確保する。

主な説明は、フルキッチン・洗濯機・ワークデスク。無料Wi-Fi、無料アメニティ、全館禁煙、英語・中国語・韓国語対応は短い一覧で整理する。言語対応をサイトの翻訳機能や常駐スタッフの保証へ置き換えない。

1階のみテラス、上階バルコニー、BBQ不可の条件を同じ位置で説明する。調理器具・食器の写真から提供数や細かな品目を断定しない。

### 05｜周辺案内・アクセス：浅草を楽しむ、東京へ出かける

前半は「01 浅草寺・雷門・仲見世通り／02 東京スカイツリー／03 かっぱ橋道具街／04 一葉記念館・浅草富士浅間神社／05 江戸たいとう伝統工芸館」の番号付きリスト。周辺観光写真が素材内に確認できないため、まず文字と線で構成する。

掲載情報：

### 07｜予約：階を選んで、旅の準備を

淡い灰緑の背景と大きなコピーで終盤の場面を切り替える。階選択は細い区切り線で分けた3行で構成し、PCは各行内に「階／設備・階段条件／予約リンク」を並べる。スマートフォンは行内を縦に組む。

| 選択肢 | 表示条件 | 行き先 |
| --- | --- | --- |
| 1階 | プライベートテラス付き・BBQ不可 | Airbnb 1階 |
| 2〜3階 | バルコニー付き・階段利用 | Airbnb 2〜3階 |
| 4〜5階 | バルコニー付き・階段利用 | Airbnb 4〜5階 |

各リンクは「Airbnbで空室・料金を確認」と明記する。別枠でBooking.comを案内する。階を指定して選んだ後にBooking.comへ移る場合も、同じ階が予約されると誤認させない。

日付・人数入力や空室表示は、実際の予約システムとの接続が確認できた場合だけ追加する。価格・最安値・予約特典は未提供のため表示しない。

予約ボタン→同じページの階選択→外部予約サイト、という導線を統一する。LINEは事前相談として配置する。

## 6. Lenis・GSAPのアニメーション設計

| 場所 | PCでの動き | スマートフォンでの動き |
| --- | --- | --- |
| 初期表示 | コピーを行単位で24px程度から立ち上げ、写真を約1.04倍から等倍へ。全体0.8〜1.2秒程度 | 移動量を半分程度に抑える |
| ページ全体 | Lenisで軽い追従感。ホイールの反応を鈍くしない | タッチは標準のスクロール感を優先 |
| コンセプト | 写真・本文の表示タイミングを少しずらす | 短いフェードと小さな移動 |
| 客室 | 左の小見出しを追従。右の写真に小さな縦移動とマスク表示。インデックスが現在位置に応じて切り替わる | 追従・視差効果を解除し縦に読む |
| 設備 | 写真と説明が0.08〜0.12秒程度の差で現れる | 移動量を抑えた順次表示 |
| 予約 | 見出しと予約リンク行が順に現れる | 操作部を早く表示する短い演出 |
| ボタン | 下線・矢印を小さく移動。キーボードフォーカスも明示 | 押した反応を明示 |

数値は実機調整前の初期案。長時間のローディング演出や入力操作を待たせる演出は設けない。ギャラリーは手動切り替えを基本とし、矢印・枚数表示・タッチ操作を用意する。

### 実装上の接続

- LenisのscrollイベントからScrollTrigger.updateを呼ぶ。
- Lenisの更新をGSAP tickerへ統合し、独立したrequestAnimationFrameを重ねない。
- gsap.matchMediaで画面幅とprefers-reduced-motionを分岐し、条件変更時は前の処理を片付ける。
- 動きを減らす設定ではLenisの補間と移動・視差演出を停止し、内容を通常表示する。
- 画像・フォントの読み込みやFAQの高さ変更が関係する位置でScrollTrigger.refreshを実行し、スクロールごとの再計算は避ける。
- ヘッダー・固定予約ボタンはアニメーション用transformを掛ける親要素から分離する。
- レイアウト用コンテナとアニメーション用の内側要素を分け、動きが周囲の寸法を変えないようにする。
- JSが動かない場合も文章・写真・予約リンクは表示し、FAQは標準のdetails要素で操作可能にする。

参考：

- Lenis公式のGSAP連携：https://github.com/darkroomengineering/lenis#gsap-scrolltrigger
- GSAP matchMedia：https://gsap.com/docs/v3/GSAP/gsap.matchMedia()/
- GSAP ScrollTrigger：https://gsap.com/docs/v3/Plugins/ScrollTrigger/

## 7. レスポンシブ・崩れ防止

PCの基本は12列グリッド。最大コンテンツ幅を1440px程度、左右余白を画面幅に応じて24〜80pxとする。写真を広く見せる箇所だけ別の外枠を使う。タブレットでは列数と余白を減らし、スマートフォンでは1列へ組み替える。

ブレークポイントはコンテンツの収まりから調整する。初期案は768px、1024px。文字を無理に縮めてPCの配置を維持しない。

1. 写真はwidth・height・aspect-ratioを確保し、読み込み前後の段差を防ぐ。
2. 大見出しはclampで範囲を決め、最小幅での日本語の改行を確認する。
3. 本文・リンク・予約行を絶対配置しない。グリッドの子要素にmin-width: 0を設け、長い文字列も収める。
4. 表現上のずれは列の位置と余白で作り、本文へ写真を重ねない。
5. 画面高さを使う箇所はモバイルのアドレスバーを考慮し、svhを基準に最低限の内容高も確保する。
6. 固定予約ボタンにはsafe-area-inset-bottomを考慮し、本文末にも同等の余白を設ける。
7. 操作領域は44px以上を目安にし、小さな文字だけを押させない。
8. ギャラリーの画像切り替えで枠高が変わらないようにする。
9. フォントは必要な書体・ウェイトへ絞り、代替フォントでも致命的な改行差が出ないようにする。
10. 不要な横スクロールは発生元を直す。ページ全体を隠して崩れをごまかさない。

## 8. 実装構成案

既存のAstroを継続する。現在のpackage.jsonはAstroのみを依存に持ち、index.astroは初期ページ。Lenis・GSAPは実装時に追加する。

```text
src/
  assets/                  支給素材（原本を保持）
  components/
    SiteHeader.astro
    Hero.astro
    StayConcept.astro
    Rooms.astro
    Amenities.astro
    NeighborhoodAccess.astro
    StayGuide.astro
    Reservation.astro
    SiteFooter.astro
  data/
    property.ts            施設・設備・FAQ情報
    reservations.ts        階別の予約リンク
  scripts/
    scroll.ts              Lenis・GSAPの初期化と終了処理
    gallery.ts             客室写真の操作
    navigation.ts          メニューとアンカー移動
  styles/
    global.css
    home.css
  pages/
    index.astro
```

## 10. 制作順序・完了条件

1. **静的レイアウト**：ロゴ・写真を実際に配置し、PCとスマートフォンの文字量・写真の切り抜きを調整。
2. **情報・予約導線**：施設情報、階別リンク、FAQ、電話・LINE・地図への接続を実装。
3. **アニメーション**：レイアウト確定後にLenis・GSAPを追加し、画面幅別に動きを調整。
4. **検証**：幅320・375・390・768・1024・1440・1920pxと、狭い高さ・横向き・200%ズームを確認。iOS Safari、Android Chrome、PC Chrome／Edge／Safariを対象に、利用できない環境は未検証として明示。
5. **公開前整備**：外部リンク、施設情報、画像代替文、キーボード操作、メニュー、動きを減らす設定、JS無効時の予約導線、ビルドを確認。

合格条件は、意図しない横スクロールがないこと、文字・写真・固定ボタンが重ならないこと、予約先と階の関係が明確なこと、低速読み込みや画面回転でレイアウトとアニメーション位置が崩れないこと。性能目標はLCP 2.5秒以内・CLS 0.1以下・INP 200ms以下とし、計測条件を添えて報告する。実利用のINP等は公開後の計測が必要になる。
